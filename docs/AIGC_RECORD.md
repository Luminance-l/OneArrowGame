# AIGC 使用记录

本项目使用 **OpenAI Codex** 辅助开发。以下内容来自 2026-09-20 的本次真实开发过程，不是项目完成后补写的虚构聊天。提交者仍需亲自运行游戏、阅读关键代码，并能解释路径检测和状态转换。

## 记录 1：需求拆解与工程结构

| 项目 | 内容 |
| --- | --- |
| 子任务 | 从课程 PDF 和步骤说明中提取硬性要求、评分重点和附加分方向 |
| 给 AI 的要求 | 在保证基础功能完整和正确的前提下完成作业，并尽量新颖、清晰、争取附加分 |
| AI 提供 | 将需求分成纯逻辑层、Pygame 界面层、测试与文档层；建议选择提示、撤销、计时/星级、进度保存和 AI 求解 |
| 实际效果 | 避免把规则全部写进事件循环，核心算法可以独立测试 |
| 人工判断/调整 | 明确“基础正确性优先”，没有加入复杂机关和外部素材，控制了功能范围 |

## 记录 2：四方向路径检测

| 项目 | 内容 |
| --- | --- |
| 子任务 | 判断箭头前方是否存在阻挡 |
| 给 AI 的要求 | 覆盖 UP、DOWN、LEFT、RIGHT，正确处理边缘，不产生数组越界 |
| AI 提供 | 使用方向枚举保存 `(dr, dc)`；从相邻格开始沿同一行/列扫描，发现首个箭头即返回阻挡，否则越界后判定可飞出 |
| 实际效果 | T01、T02、T03 和四方向参数化测试全部通过 |
| 人工判断/调整 | 用“边缘朝外箭头”和“四个方向各放一个阻挡物”的用例检查，确认扫描起点不是箭头自身 |

## 记录 3：关卡设计与可解性验证

| 项目 | 内容 |
| --- | --- |
| 子任务 | 设计至少 3 个可通关关卡，并避免只凭肉眼判断 |
| 给 AI 的要求 | 生成 5 个原创关卡，数量递增，同时用算法证明存在完整通关序列 |
| AI 提供 | 设计 6、10、15、17、24 支箭的五关，并编写 BFS 求解器验证 |
| 实际效果 | 第一轮测试发现第 5 关返回 `None`，说明存在无法打破的阻挡循环 |
| 人工判断/调整 | 保留布局，仅把第 5 关 `(3, 1)` 的方向从 `UP` 调为 `LEFT`；再次运行后五关分别得到 6、10、15、17、24 步解，并加入永久回归测试 |

## 记录 4：界面、动画与视觉检查

| 项目 | 内容 |
| --- | --- |
| 子任务 | 设计清晰、原创的界面和明显碰撞反馈 |
| 给 AI 的要求 | 不使用商业游戏素材；提供飞出淡出、碰撞晃动/变红、开始/通关/失败界面和可用于 README 的截图 |
| AI 提供 | 米白纸张风格界面、四色矢量箭头、按钮组件、飞出动画、红色晃动与 `BLOCKED` 提示，并提供 `--capture` 截图模式 |
| 实际效果 | 真实 Pygame 环境生成 5 张 1000×760 截图；首次截图发现装饰符号在中文字体下显示为方框 |
| 人工判断/调整 | 删除按钮中不兼容的装饰符号，并冻结结算页计时，重新生成并逐张检查，无重叠、裁切或方框字 |

## 记录 5：测试与文档

| 项目 | 内容 |
| --- | --- |
| 子任务 | 将课程 T01–T06 变为可重复执行的自动测试 |
| 给 AI 的要求 | 测试不依赖窗口和人工点击，覆盖成功、阻挡、边界、通关、失败和重开 |
| AI 提供 | 基于 `unittest` 的 10 个测试，以及 GitHub Actions 工作流 |
| 实际效果 | Python 3.12 下 10/10 通过；核心逻辑测试约 6 秒完成 |
| 人工判断/调整 | 发现最初测试错误地把一个无遮挡坐标当作阻挡坐标，改用 Level 1 的 `(2, 2)` → `(2, 4)` 真实阻挡关系后通过 |

## 对 AI 输出的反思

AIGC 最有价值的地方不是一次生成很多代码，而是快速给出可检验的结构和测试思路。本次开发中，AI 初版关卡和初版测试都出现过问题；如果只看界面、不运行求解器和自动测试，这些错误很容易进入最终提交。我的结论是：AI 适合加速实现，但“能运行、可通关、符合题意”必须由自动测试和人工试玩共同确认。
